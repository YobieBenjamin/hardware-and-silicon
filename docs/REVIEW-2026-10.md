# Design review, October 2026: what was said and what changed

A chip designer reviewed the first draft of the silicon design (the post now at
[`blog/04-the-chip-that-says-no-3-the-silicon-design.md`](../blog/04-the-chip-that-says-no-3-the-silicon-design.md)).
His overall verdict: worth prototyping; the independent hardware gate at the action
endpoint is the strongest part; the first draft promised more than the proposed hardware
could establish; turn the architecture into a narrower, testable security contract. He
checked the hardware assumptions against NVIDIA's CUDA and attestation documentation and
against seL4's verification notes.

Seven points, all adopted. This file records each one, what it changed, and where the
change lives, so the reasoning survives the edits. The reviewer's own text is not
reproduced here; it was a private note.

| # | Point | What changed | Where |
|---|---|---|---|
| 1 | A companion chip per CPU/GPU/memory combination is a packaging choice, not an enforcement boundary; a chip governs only paths over which it has non-bypassable authority; a halt line cannot undo an action that already escaped | The unit of protection is now an **enforcement domain** (processors, memory, interfaces and action endpoints whose exits are all controlled). The endpoint gate is the **primary guarantee**; the compute-side silicon is containment and provenance. The placement table gained the endpoint row (E) alongside A/B/C | `blog/04` §Enforcement domains; `docs/CHIP_DESIGN.md` §2; `docs/SILICON.md` §3 |
| 2 | "Everything is a DMA descriptor" is wrong: CUDA threads can load and store directly in peer-GPU memory, so a copy-engine descriptor check misses that traffic | One mediating governor became a **small policy controller plus distributed enforcement points**: descriptor checks on copy engines, roster-bound peer mappings and link keys for thread-initiated peer access, RDMA filter tables on the DPU, a storage-channel capability for GPUDirect Storage, and "disabled by policy" for any path without a checker. A PCIe prototype validates its own boundary only | `blog/04` §The policy controller and its enforcement points; `docs/CHIP_DESIGN.md` §5 |
| 3 | The output signature establishes less than claimed: a compromised runtime can fill the output buffer and the controller will sign it under the approved model's hash; `prompt_hash` is a claim by the serving stack; the signature is a detachable record, not a watermark | Provenance split into **device provenance** (buildable), **workload provenance** (attested runtime's own record; buildable) and **execution integrity** (open research, candidates listed). The record's `prompt_hash` is labelled "as claimed". The watermark lane stays a separate tool | `blog/04` §Provenance; `docs/CHIP_DESIGN.md` §6; Appendix D |
| 4 | Every external action should pass authorization; reversible/irreversible decides how much checking and delay, never whether; the first draft let the broker execute "reversible" actions directly while the authority table said it could not | **Every action is authorized.** The rule's `requirement.mode` (`auto` / `observer` / `human`) is the fast or slow path. Requester-supplied labels are ignored by construction (rules are selected from measurement, action and constrained parameters only). New catalogue attack `TX.risk_label_ignored`. The contradiction is gone | `gate.py` (unchanged selection logic, now documented), `attacks.py`; `blog/04` §The gate |
| 5 | The declaration-to-action binding needs a transactional design: bind the exact operation, amount, currency, recipient, destination service, policy version and action id; replay protection that survives restart; coordinate check, reserve and commit; several correct governors can still overspend a shared allowance | New `ledger.py` (`StateStore`, `DurableState`): durable replay state, holds and rate windows; **reserve at allow, commit at the endpoint before execution, release at ticket expiry**, one lock around check → reserve → mint; **policy epochs** on tickets, checked by endpoints; **endpoint binding** on tickets; the gate key is DICE-style derived so a restart keeps it; `Node.restart()`; fail-closed when the gate is unreachable at commit time. One ledger owns a budget key | `hardware_ref/ledger.py`, `gate.py`, `endpoints.py`, `policy.py`, `system.py`; `tests/test_transactional.py`; the `TX` block of the catalogue |
| 6 | Trusted hardware does not make declared facts true: the chip compares a supplied value against a protected rule and still needs a justified basis for trusting the value; agreeing sensors are not independent sensors; the novelty detector is an extra reason to stop, not a guarantee | An **assumptions register** per deployment: which inputs are authoritative, freshness, behaviour on conflict, what the hardware cannot check. The novelty check is reclassified as a witness (Layer 3) rather than a guarantee. Hypothesis CONTRACT-ASSUMPTIONS-REGISTER-COMPLETE tests the register's completeness | `blog/04` §The assumptions register; `docs/CHIP_DESIGN.md` §4 |
| 7 | Tighten the absolute claims: "no weights can leave", "software tests everything except tamperproofness", "alarms only improve safety", "failure means an action not taken", "a small verified controller makes the stack verifiable"; keep the under-one-percent overhead as a target with separate measurements for the governor and for the whole deployment | A **tightened-claims table** adopted verbatim in spirit; a leakage threat model for permitted channels; per-application safe transitions; seL4's assumption list cited as the model for writing down proof assumptions; two performance measurements | `blog/04` §Tightened claims, §Performance budget; `docs/CHIP_DESIGN.md` §8 |

## The recommended first build, and its status

The reviewer suggested starting with an action governor for one benign domain (a
simulated payment service or a protected file store), keeping the model outside the
trusted core, giving the endpoint a gate the host cannot bypass, and demonstrating five
things. All five are now in the reference stack and run with `./run.sh`:

1. Allowed operations succeed: `baseline.pay_small`, `baseline.pay_large_hold_approve`, `baseline.budget_recovers_after_ticket_expiry`.
2. Forged, altered, expired and replayed approvals fail: the `EP` block, `L4.approval_*`, `TX.commit_forged_ticket`.
3. Concurrent requests cannot exceed a shared budget: `TX.concurrent_overspend`, `TX.budget_exhausted`.
4. Host compromise cannot bypass endpoint authorization: `EP.no_ticket`, `TX.risk_label_ignored`, `TX.epoch_forged`, `L5.policy_forged`.
5. Restart, power loss, policy changes and network partitions preserve the specified behaviour: `TX.ticket_replay_after_restart`, `TX.request_replay_after_restart`, `baseline.hold_survives_restart`, `TX.ticket_after_policy_change`, `TX.commit_unreachable`.

Then, as separately tested capabilities: workload attestation of the serving stack, and
compute-side containment on a DPU (Phase 2 in `docs/PROTOTYPING.md`).

## The contract, as adopted

> Within a declared enforcement boundary, every protected operation requires a fresh
> authorization bound to that exact operation. The endpoint enforces specified invariants
> independently of the proposing model, subject to explicit assumptions about its inputs,
> its hardware, and its policy authority.
